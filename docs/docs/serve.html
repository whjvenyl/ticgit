Web View

Command: ti serve

ti serve starts a small read-only HTTP server that lets you browse your tickets in a web browser. No external dependencies, no database — it reads from the same git-meta store as the CLI and TUI.

SERVE
$ ti serve
ti serve: listening on http://127.0.0.1:8177/ (ctrl-c to stop)

Open the page automatically in your browser:

SERVE & OPEN
$ ti serve --open

Options

OPTIONS
$ ti serve --port 8080 --bind 0.0.0.0 --open
  • --port / -p — port to listen on (default 8177, use 0 for a free port)
  • --bind — address to bind (default 127.0.0.1, use 0.0.0.0 to share on your network)
  • --open — open the page in your browser on start

Views

The web view has two list modes (List and Kanban), switchable from the nav bar, plus a per-ticket Lifecycle view. All list views share the same filters (status, state, tags, assigned, search), so you can narrow to e.g. ?tag=bug and see only bug tickets in any view.

List

The default view at /. A sortable table of tickets showing id, age, priority, state, title, assignee, and tags. Subissues are grouped under their parent with an expandable [+N] toggle and indented rows. Click a ticket to see its detail page at /t/<id>.

LIST VIEW
$ ti serve
# opens at http://127.0.0.1:8177/
# table with sortable columns, filter chips, search

Kanban

A board view at /kanban. Tickets are grouped into columns by lifecycle state:

KANBAN VIEW
$ ti serve
# navigate to /kanban or click "Kanban" in the nav
 
new assigned in-progress blocked review
+------ +------ +------ +------ +------
| card | | card | | card | | card | | card |
+------ +------ +------ +------ +------

Each card shows the ticket id, title, priority, assignee, and tags. Subissues are nested under their parent card with an expandable [+N] toggle. Click a card to open the detail page. Empty closed-state columns (resolved, wontfix, etc.) are hidden to reduce clutter; they appear when closed tickets match the active filter.

Lifecycle

A per-ticket state-transition graph at /t/<id>/flow, linked from each ticket's detail page. It reconstructs the ticket's state history from the git-meta metadata log and renders the journey through its states over time, rendered with React Flow.

LIFECYCLE VIEW
$ ti serve
# open a ticket detail page, then click "Lifecycle"
# or go directly to /t/<id>/flow
 
[new] —#1·2d—> [in-progress] —#2·5h—> [review]
<-#3·1h— (back-edge: revisited)
[review] —#4·3d—> [resolved ✓]

The graph shows one node per unique state, positioned left-to-right by first visit. Edges represent transitions and are labeled with their sequence number and the duration spent in the source state. Loops — a ticket that bounces review → in-progress → review — draw as dashed red back-edges so revisited states are immediately visible. Nodes visited more than once get a ×N badge; the current state node has a highlighted border.

Below the graph, a timeline lists every field change grouped by the state window it happened in: comments added, tags changed, assignment updates, priority/points set, etc. Each step shows a timestamp and who made the change. This mirrors the GitHub Actions pattern of a job graph on top and a step log beneath.

React, ReactDOM, and @xyflow/react are bundled locally (no CDN dependencies) and the view respects the system dark/light theme. Nodes are draggable; pan (drag) and zoom (scroll) work as expected.

Filtering

The List and Kanban views accept the same query parameters as ti list:

FILTERS
$ # open in browser:
http://127.0.0.1:8177/?tag=bug
http://127.0.0.1:8177/kanban?state=blocked
http://127.0.0.1:8177/?assigned=you@example.com&all=1

Supported params: status, state, tag (repeatable), assigned, q (search), order, all.

Subissues are always included in all web views and the JSON API. In the list and kanban views, subissues are grouped under their parent with an expandable [+N] toggle.

JSON API

/tickets.json returns the filtered ticket list as a JSON array, accepting the same query params:

JSON
$ curl http://127.0.0.1:8177/tickets.json?tag=bug
[{"id":"a3f...","title":"fix parser",...}]

Detail Pages

Each ticket has a detail page at /t/<id> showing all fields, description, spec, and comments. The id can be a full UUID or any unique prefix. A Lifecycle link in the detail page header opens the per-ticket state-transition graph at /t/<id>/flow.

DETAIL
$ # open in browser:
http://127.0.0.1:8177/t/a3f
